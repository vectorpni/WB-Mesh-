# Предварительное решение по архитектуре

Статус: план подготовки, реализация не начиналась.

| Вариант | Изменения и совместимость | Эксплуатация, RAM, безопасность и целостность | Вывод |
|---|---|---|---|
| A: Node + Python геосервис | Сохраняет Python OSRM-код, но требует двух процессов и контракт между ними | Два runtime, два деплоя, дополнительная сеть; транзакции всё равно должны быть на одном сервере | Только если Python-библиотека оптимизации даёт измеримое преимущество после прототипа |
| B: Flask основной | Использует 15 API, но переносит всю V8 бизнес-логику из JS или оставляет два ядра | Удобная SQLite в Python, но переписывание V8 и двойная модель — высокий риск | Не принимать без нового доказательства |
| C: Node основной, адаптация геоалгоритмов | Сохраняет V8 ядро/интерфейс; переносит небольшой OSRM HTTP-адаптер и Leaflet UI | Один процесс и одна БД SQLite; меньше памяти и операционных частей; транзакции через единый сервер | **Предпочтительно по текущим исходникам**, уточнить после будущих интеграционных замеров |

Граница ответственности: сервер — единственный владелец заказа, остатка, решения MCS, тарифа, журнала, рейса и маршрута; браузер — представление и запросы. Экономика V8 остаётся единственной авторитетной моделью. Геосервис выдаёт геометрию/дистанцию/время/статус источника, а не назначает тарифы. Leaflet показывает данные сервера. Это план, не описание существующего Backend.

Перед реализацией: зафиксировать OpenAPI-контракт, инварианты запасов и денежных сумм, сопоставление ID/узлов; создать тесты на M1, возвраты, повторный SKU, конкурентный резерв, аварийный commit; лишь затем перенести операции постепенно. Текущий Node `server.js` — раздатчик файлов, не готовый Backend (`src/server-policy.js`).
