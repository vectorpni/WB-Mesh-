# План миграции CSV → SQLite

Источник: девять `TABLE_SCHEMAS` (`app.py:59–169`). `CsvStore` пишет таблицы по одной, а `tx()` удерживает только внутрипроцессный замок (`172–269`); это не межтабличная транзакция. В V8 клиентское состояние дополнительно живёт в localStorage, поэтому перед миграцией нужен единый владелец данных.

1. Зафиксировать схему единой БД: `nodes`, `products`, партии/остатки, `orders`, строки заказа, резервы, перемещения, возвраты/проверки, транспорт/рейсы, `events`, `ledger`, конфигурация и версии. FK, CHECK для неотрицательных количеств, уникальность ключа идемпотентности и индексы на SKU/узел/статус.
2. Сохранить исходные CSV неизменными и записать их SHA-256/счётчики строк. Для V8 JSON установить миграционный формат и таблицу соответствия ID. Нельзя одновременно принимать записи в CSV, localStorage и SQLite как равноправные источники.
3. Сухая загрузка в новую SQLite-базу: валидация `P=A+R+Q+D`, связей, сумм T_in, дублей ID и расчётов, составление отчёта отклонений. Ошибки не исправлять молча.
4. Версионированная миграция в транзакции; для приёма, резерва, отправки, прибытия, выдачи и возврата — атомарная запись состояния и события/начисления. Повторы возвращают прежний результат по уникальному idempotency key; конкурентные операции сериализуются и повторно проверяют остаток после блокировки.
5. Тест аварийного завершения между операциями, конкурентных заказов, повторных запросов, восстановления БД и сравнения снимков до/после. PostgreSQL/PostGIS рассматривать только при доказанной потребности в многопроцессной записи и пространственных запросах.
