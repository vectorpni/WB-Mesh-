# Навигация Core V2: что сохранять и что исправить

Сохранять структуру OSRM Route/Trip запроса (`app.py:380–399`), реальную GeoJSON-линию, расстояние и длительность (`401–419`), `haversine_km()` только как оценку (`296–301`).

Исправить до показа: M1=0 км/0 минут движения и нет рейса (`349–368,630–652`); совпавшие координаты не заменять фиктивными (`370–378`); fallback с коэффициентами показывать пунктиром и без манёвров (`322–346`); при нехватке GeoJSON не маркировать fallback как OSRM (`416–418`). Пошаговые инструкции, улицы, ETA, прогресс, перестроение, автомобиль и груз в архиве отсутствуют; это будущие функции, а не готовый навигатор. Trip оптимизирует порядок точек, но не учитывает вместимость и временные окна; для CVRP нужен отдельный решатель/алгоритм.

Проверки после разрешения разработки: M1, совпадающие/разные координаты, ошибочный OSRM, сохранённый дорожный маршрут, альтернативы и Table API при поддержке, геолокация только с согласия пользователя, независимость расчёта стоимости от происхождения линии.

## Контракт части 3/5, блока 8/10

Серверный ответ для навигации должен связывать один заказ/рейс, выбранные источники А1…Аn, конечный ПВЗ Б, остановки, геометрию с явным происхождением, манёвры из маршрутизатора при наличии, текущий сегмент, статусы груза, загрузку, виртуальное время и происхождение положения транспорта. Карта и панель читают этот ответ, а не ведут отдельное состояние. Название улицы показывается лишь при наличии в ответе дорожного графа; для `estimate` и `unavailable` нет пошаговых манёвров.

Поля панели: следующий манёвр, расстояние до него, улица при наличии, оставшиеся километры и минуты движения, ETA, скорость с меткой «симуляция» либо подтверждённым источником, текущая/предельная загрузка, состояние груза и следующая остановка. Время доставки разделять на ожидание, поиск/сборку, погрузку, движение, разгрузку, обработку и прочие подтверждённые операции. Формула `T_total = T_wait + T_pick + T_load + T_drive + T_unload + T_process + T_other` описывает последовательный путь; при параллельных действиях рассчитывать длительность по зависимостям/критическому пути и не суммировать перекрытые интервалы дважды. Показывать предположения и источник каждой длительности.

Для рейса `Progress = 100×D_passed/D_total`, ограниченный диапазоном `[0,100]` при `D_total>0`. Движение в демо интерполировать **по дорожной геометрии**, связывая пройденную длину, виртуальное время, остановки, загрузку и ETA. Скорость ×1/×5/×10/×50 ускоряет виртуальные часы, а не утверждает реальную скорость автомобиля. Пауза останавливает симуляцию. Для M1 `D_total=0`, автомобиля/манёвров/рейса нет; показывать операционный статус заказа вместо дорожного прогресса.

Сервер сохраняет состояние часов, активного рейса, положения и последнего обработанного события так, чтобы перезагрузка страницы восстанавливала согласованный снимок и не дублировала операции. Перестроение маршрута начинает новый версионированный расчёт от подтверждённого или явно симулированного положения товара, сохраняет прежний маршрут в истории и повторно проверяет вместимость, сроки и экономику. История маршрутов содержит исходные/конечные точки, остановки, геометрию или ссылку на неё, источник (`road_live`/`road_cached`/`estimate`/`unavailable`), время расчёта, версии и причины изменения. Пробки и GPS не объявлять реальными без внешнего подтверждённого источника и согласия на геолокацию.

Будущие проверки: M1 без деления на ноль; совпадающие точки; отсутствие манёвров у fallback; параллельная погрузка и ожидание без удвоения `T_total`; прогресс на линии/остановке/по прибытии; пауза и все множители часов; восстановление после перезагрузки; перестроение от положения груза с неизменной историей. **Тесты не выполнены**.
