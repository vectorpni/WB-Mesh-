# Order Backend & Extreme Killcritic — подготовительный контроль

Статус: часть 3/5, блок 10/10. **Только требования и критерии будущей приёмки.** Server V8 сейчас статический; Flask Core V2 не запускался из-за отсутствующей зависимости. Наличие API в `app.py` и этот документ не подтверждают работоспособность.

## Единая цепочка и запись состояния

`Товар → выбранный покупателем ПВЗ Б → подтверждённые источники А1…Аn → допустимые планы MCS → карта из того же снимка → экономика четырёх сторон → подтверждение → атомарное резервирование → перевозка → выдача`.

Единая серверная БД должна хранить узлы/продавцов/товары, партии и раздельные физический/доступный/зарезервированный/карантинный/бракованный/транзитный статусы, заказы и строки, распределение по источникам, резервы, рейсы и версии дорожной геометрии, сроки и тарифные версии, расчёты/начисления и неизменяемый журнал событий. Идентификаторы связывают карточку заказа, карту, MCS, транспорт и финансовую расшифровку. Дублирующего состояния заказов в браузере или второго финансового ядра нет.

**Планирование** читает согласованный снимок и возвращает кандидатов/причины отказа, но не изменяет физический запас, резерв и начисления. **Подтверждение** по идемпотентному ключу и версии предложения внутри транзакции повторно проверяет продавца, партии, доступность после чужих резервов, карантин/брак, узлы, вместимость, сроки и тариф. Заказ, строки, назначения, резервы и событие записываются вместе; при ошибке все изменения откатываются. Внешний OSRM вызывается вне открытой транзакции; после ответа версии и ограничения перепроверяются.

Списание при передаче/выдаче разрешено только по резерву данного заказа и допустимому переходу статуса. Возврат связывается с фактически выданной единицей, не превышает ещё не возвращённое количество и поступает в карантин до проверки. Отмена освобождает только собственный резерв и учитывает стадию перевозки. Повторное подтверждение, отмена, выдача, возврат и начисление с тем же ключом должны возвращать прежний результат без второго физического или денежного эффекта. История сохраняет причины выбора и отклонения каждого кандидата MCS.

## Приоритеты и границы

| Приоритет | Приёмка будущей реализации |
|---|---|
| P0 | Корректные заказы, достоверные А и Б, M1/M2/C1/C2 без фиктивной подмены, единая экономика, атомарный резерв, согласованность БД/API/UI; все подтверждённые дефекты Core V2 исправляются до принятия затронутого компонента |
| P1 | Мульти-ПВЗ, навигатор, оптимизация, отслеживание, Mathematical Lab — только после надёжной базы P0 |
| P2 | Monte Carlo и дополнительная аналитика — после P0/P1 |

Этот порядок описывает объём поставки, а `CORE_V2_P0_FIXES.md` — обязательность устранения уже обнаруженных дефектов даже в компоненте, который относится к функциональному этапу P1. Не отмечать компонент готовым на основании документов.
