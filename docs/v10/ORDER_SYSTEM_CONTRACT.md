# Intelligent Order System — подготовительный контракт

Статус: часть 3/5, блок 2/10. **Проектное описание, не реализованная функция.** Исходный V8 содержит товар, продавца, партии, резерв и MCS; V10 пока не имеет единого серверного оформления заказа, настоящей географической карты и постоянной БД. Разработка запрещена до всех пяти частей и отдельной команды запуска.

## Один путь заказа

1. Покупатель выбирает товар, продавца, количество и складывает строки в корзину. Совпадающие SKU одного продавца агрегируются для проверки запаса; отдельные строки сохраняют цены и происхождение.
2. Покупатель выбирает город и **конечный ПВЗ Б** на карте. Сервер подтверждает его статус, часы работы, ограничения приёма и вместимость на ожидаемое время доставки.
3. Order Allocation Engine ищет физические партии только выбранного продавца на ПВЗ, хабах и складах. Доступно лишь `физический остаток − действующие резервы` для пригодных к продаже партий; карантин, брак и товар в пути не считаются доступным запасом. Для каждой строки проверяются категория, габариты и количество.
4. MCS строит допустимые кандидаты M1/M2/C1/C2 из подтверждённых источников, показывает срок, стоимость, происхождение дорожного маршрута, ограничения и причину отказа. При нескольких источниках план содержит распределение количества по каждому узлу, а не вымышленный единый источник. Клиент получает предложение с версией снимка и временем действия, не созданный заказ.
5. При подтверждении сервер повторно проверяет запас, резервы, продавца, статус узлов, вместимость, часы, тариф и предложение. В **одной транзакции** записывает заказ/строки, резерв по партиям, назначения источников, событие и идемпотентный ответ. Если версия или условия изменились, предложение пересчитывается; частичный заказ и двойной резерв недопустимы.
6. Отслеживание читает те же серверные события и статусы заказа, резерва, передачи, рейса, приёмки и выдачи. ETA меняется только после проверенного пересчёта; отсутствие дорожного пути и недоступность OSRM отображаются явно.

## Контракт карточки и карты

В каждой карточке заказа крупно выводятся **«ОТКУДА ВЕЗЁМ»** и **«КУДА ДОСТАВЛЯЕМ»**. Для каждого узла: ID, адрес либо маркировка «демонстрационный объект», город, координаты с происхождением, доступное количество выбранного SKU, статус и причина ограничения. При нескольких источниках показываются А1, А2 и количество из каждого; Б остаётся выбранным покупателем ПВЗ. Маркеры карты и карточка используют один ответ Backend, без собственного клиентского остатка. M1 допускает А=Б, 0 км автомобильного пути и отсутствие рейса.

## Серверные инварианты для будущей реализации

- Покупатель задаёт Б; MCS выбирает А и маршрут. Источник нельзя назначить без подтверждённой партии и продавца.
- Доступный остаток неотрицателен; сумма резервов по партии не превышает пригодное физическое количество. Повторный запрос с тем же идемпотентным ключом возвращает тот же заказ.
- Все строки корзины подтверждаются вместе либо ни одна. Конкурентные подтверждения одной партии сериализуются транзакцией БД.
- Варианты маршрута сравниваются по единой тарифной версии и четырёхсторонним ограничениям V8. Не переносить тарифы Core V2 65/76/106/132 ₽ в контрольную экономику.
- Адрес, координаты, остаток и статус не выдумываются. Синтетические координаты явно подписываются; при отсутствии координат выбор ПВЗ и список сохраняют смысл, дорожный маршрут помечается недоступным.
- Заказ без допустимого источника или маршрута получает объяснимый отказ, а не фиктивное подтверждение.

## Критерии проверки после разрешённой реализации

| Сценарий | Ожидаемый проверяемый результат |
|---|---|
| Одна локальная пригодная партия | M1, А=Б, без автомобильного рейса; точный запас и продавец |
| Два источника для одной корзины | Раздельные А1/А2, объёмы и резервы; одна точка Б |
| Дублирующиеся SKU и два одновременных подтверждения | Никакого превышения запаса или двойного резерва |
| Карантин, брак, чужой продавец | Источник исключён с причиной |
| Закрытый/переполненный ПВЗ | Невозможность подтверждения либо допустимое новое предложение без молчаливой подмены Б |
| Изменение статуса между расчётом и подтверждением | Повторная проверка и атомарный отказ/перерасчёт |
| Перезагрузка страницы | Заказ, карта и отслеживание согласованы с сервером |

Это критерии будущих тестов, **не результаты тестирования**. Дефекты Core V2 и обязательные исправления перечислены в `CORE_V2_P0_FIXES.md`.
