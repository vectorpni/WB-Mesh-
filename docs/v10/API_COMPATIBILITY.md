# Core V2 API: подготовительный контракт

В `app.py:1084–1503` определены `GET /healthz`, `GET /api/state` и 13 POST-маршрутов: `/api/mesh/toggle`, `/api/nodes/<nid>/status`, `/api/nodes/<nid>/categories`, `/api/stock/receive`, `/api/orders`, `/api/multi-orders/plan`, `/api/multi-orders`, `/api/multi-orders/<moid>/arrive`, `/api/orders/<oid>/step`, `/api/transfers`, `/api/transfers/<tid>/arrive`, `/api/returns`, `/api/returns/<rid>/resolve`. Маршруты прочитаны в исходнике; HTTP-выполнение не проверено.

Существующий `server.js` V8 отдаёт только статические файлы; прямого совпадения REST-контракта нет. Будущий единый OpenAPI должен определить request/response schema, идентификаторы, ошибки 400/404/409/5xx, роли и права, ключи идемпотентности, версии состояния, транзакционные гарантии, координаты/происхождение маршрута и денежные суммы в копейках. Сохранить семантику полезных операций Core V2, но не переносить его ошибки и float-тарифы.

Приоритет контрактных проверок: неверный `qty` (`int(...)` сейчас может дать 500), строковое `enabled='false'` сейчас превращается в `True` (`app.py:1163–1168`), повторный POST заказа, повторный SKU, выдача до прибытия, возврат без выданного заказа, недоступный хаб, отказ OSRM и скрытие внутреннего `data_dir` в healthcheck. Авторизация в архиве не реализована. Реализация OpenAPI и реальные API-тесты отложены до команды запуска.
